# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

InnerStock is a trading-journal and portfolio app. Users log trades (or sync them from Wealthsimple through SnapTrade), and every manual trade needs a written thesis, a conviction score and a review date. The app shows holdings and P&L from live yfinance prices, brings trades back for grading when their review date arrives, flags behaviour patterns such as FOMO, and offers a Claude-backed advisor chat plus per-ticker news sentiment and bull/bear summaries.

- `Backend/`: FastAPI + SQLAlchemy + SQLite (`innerstock.db`)
- `Frontend/`: React 19 + Vite, plain JS/JSX (no TypeScript), Recharts for charts

## Commands

Backend (run from `Backend/`, with the venv in `Backend/venv` activated):
```
pip install -r requirements.txt
python init_db.py                 # apply all Alembic migrations (= alembic upgrade head)
uvicorn main:app --reload         # serves on http://127.0.0.1:8000, Swagger at /docs
```
Copy `Backend/.env.example` to `Backend/.env`. `ANTHROPIC_API_KEY` and `JWT_SECRET_KEY` are required; `DATABASE_URL` (defaults to local SQLite) and the `SNAPTRADE_*` keys are optional.

Schema changes go through Alembic (run from `Backend/`):
```
alembic revision --autogenerate -m "describe change"   # then review/edit the generated file
alembic upgrade head
alembic check                                        # models and migrations agree?
```
`env.py` uses the app's own engine (`database.DATABASE_URL`) and `render_as_batch=True` because SQLite can't ALTER most things in place. Migration `0001` is a baseline that also upgrades pre-Alembic databases in place (creates missing tables, adds missing columns), so existing local DBs never need deleting.

Frontend (run from `Frontend/`):
```
npm install
npm run dev       # http://localhost:5173
npm run build
npm run lint
```

Backend tests (run from `Backend/`):
```
pip install -r requirements-dev.txt
python -m pytest                                   # whole suite
python -m pytest tests/test_holdings.py -k rebuy   # single file / test
```
Tests use a fresh in-memory SQLite DB per test and stub out yfinance (`prices` fixture replaces `get_or_fetch_price`) and the FOMO check; the `history` fixture fakes daily closes for the grading scorecard (`grading.fetch_daily_closes`, keyed by ticker, missing ticker = no data). `conftest.py` sets fake `JWT_SECRET_KEY`/`ANTHROPIC_API_KEY` and blanks the `SNAPTRADE_*` vars so no real API can be hit; brokerage tests use the `fake_snaptrade` fixture in `test_snaptrade_sync.py`. `test_migrations.py` fails if `models.py` changes without a matching migration. Use the `alice`/`bob` fixtures and `log_trade()` helper from `tests/conftest.py`. When adding a user-scoped route, add it to the isolation tests in `test_data_isolation.py`.

CI (`.github/workflows/ci.yml`, runs on PRs to `main`) runs `py_compile` and pytest with Python 3.14 and `npm run build` with Node 20.

## Architecture

### Backend
- **Most logic lives in `Backend/main.py`**: nearly every route, the Pydantic request models, the price cache and the Claude calls. `models.py` holds the ORM tables, `auth.py` handles bcrypt and JWT (HS256, 7-day tokens), `database.py` builds the engine from `DATABASE_URL`, and `deps.py` holds the shared `get_db`/`get_current_user` dependencies. New route groups go in their own module with an `APIRouter` included from `main.py` (e.g. `brokerage.py`), importing dependencies from `deps.py` rather than `main`.
- **Imports are flat** (`from models import ...`), so the backend has to be run from inside `Backend/`.
- **Auth**: protected routes take `current_user: User = Depends(get_current_user)` (from `deps.py`), which uses an `HTTPBearer` token. Any route touching user data must filter by `current_user.id`. Public routes such as `/stock/{ticker}`, `/sentiment/{ticker}` and `/bullbear/{ticker}` take no user.
- **Migrations**: every model change needs an Alembic migration in `migrations/versions/` (see Commands). Each developer keeps their own gitignored `innerstock.db`, upgraded with `python init_db.py`.
- **Price data**: always go through `get_or_fetch_price(ticker, db)` rather than calling yfinance directly. It reads the `PriceCache` table (TTL `PRICE_CACHE_TTL_SECONDS` = 45s), falls back to stale cache when yfinance fails, and uses `regularMarketPrice` when `currentPrice` is missing (ETFs such as `VFV.TO`). Tickers are upper-cased.
- **Canadian tickers**: `.TO` (TSX) tickers are first-class. Trade times are treated as US/Eastern. Sentiment tells TSX ETFs apart from CDRs using yfinance `quoteType`; never guess a US ticker by stripping `.TO` (see the comments in `get_sentiment`).
- **Claude usage**: one module-level `claude_client`.
  - Sentiment and bull/bear use `claude-sonnet-4-6`. Sentiment results are cached in `SentimentCache` for 60 minutes, and ETFs with no news get a permanent `"unavailable"` marker.
  - The advisor (`advisor.py`: `POST /chat`, `GET /chat/suggestions`) uses `claude-opus-5-5` with a manual tool loop (max `MAX_TOOL_ROUNDS` = 6 lookup rounds; the last forces `tool_choice: none`). The system prompt is two blocks: the stable `ADVISOR_INSTRUCTIONS` (prompt-cached) and the per-message facts from `main.build_advisor_context` (profile, holdings, fundamentals, recent trades, reasons, sector exposure, watchlist, due reviews, unread recaps). Tools are read-only and user-scoped: `get_stock_snapshot`, `get_price_performance`, `get_company_news`, `get_earnings`, `get_my_trades`, `get_trade_review`, `get_portfolio_breakdown`, `simulate_trade`; add new ones to `TOOLS` + `_TOOL_FUNCTIONS` + `tool_label`. It sends the newest 40 `ChatMessage` rows (by id), stores the user message before calling Claude, stores only the final text, and returns `tools_used` labels. Suggestions are rule-based (no Claude call). Tests use the fake client in `tests/test_advisor.py`.
  - Earnings recaps (`earnings_recaps.py`) use `claude-opus-5-5` (medium effort, structured JSON output via `output_config.format`, `fallbacks: "default"` refusal fallback) with their own pricing constants; they reuse `main.claude_client` and the `analysis` rate-limit bucket (imported lazily, since `main` imports the module).
  - Each call prints its token usage and estimated cost to the terminal. If you change models, update the pricing constants.
- **Holdings math** (`/holdings`): processes trades in date order with moving-average cost basis (ACB). A separate tracker for today's buys keeps day gain/loss correct for shares bought today.
- **Trades**: manual trades go through `POST /trades` (`TradeCreate` requires a thesis, conviction, review date and `trade_time`). `Trade.source` is `manual`, `csv` (legacy rows from a removed CSV import) or `snaptrade`. Synced trades have no thesis, so `/trades/incomplete` lists them. Grading happens through `PATCH /trades/{id}/outcome`.
- **Grading** (`grading.py`): `GET /thesis-reviews/{id}/scorecard` gives a due trade's evidence - its return and the S&P 500's over the same days (currency-matched: `VFV.TO` for Canadian listings, `SPY` for US; S&P 500 funds are judged alone), best/worst since the trade, a price series, the stored FOMO check (`fomo.stored_result`) and a suggested grade. Returns are measured at the trade's `review_date` (not today) so waiting for a bounce doesn't change the verdict. `apply_grade` validates the outcome, requires `review_notes` when the grade flatly contradicts the suggestion (correct vs incorrect), and stores a snapshot (`graded_at`, `suggested_outcome`, `graded_return_pct`, `graded_benchmark_return_pct`) that `reasons_summary` turns into average return / vs-market per reason. All price history goes through `fetch_daily_closes` / `fetch_daily_volumes` (one cached yfinance download per ticker+range, `_fetch_bars`, 10-min in-memory cache); fill prices far from the trade-day close are treated as a later stock split. `GET /thesis-reviews` first runs `grading.auto_grade_due`: due trades whose numbers can judge them (a close exists on/after the review date, and there's a suggestion) are graded with the suggested grade and `auto_graded = True` (max 20 per request, scorecards computed in parallel); only the rest are returned for the user. Re-grading through `PATCH /trades/{id}/outcome` follows the same rules and sets `auto_graded = False`.
- **FOMO check** (`fomo.py`, `POST /fomo/check`, `GET /fomo/summary`): every buy gets a 0-100 score and a band (`chasing` 60+, `warm` 30+, `calm`, `dip` for a sharp drop, `unknown` with <25 sessions of history). Market signals: the 5-day run-up minus the benchmark's, divided by the stock's own normal 5-day move (60-session volatility measured *before* that week) = z-score (+30 at 2+, +15 at 1.5+); within 3% of the 20-day high after a run-up (+10); volume 2x+ the 20-day average (+15); a one-day jump of 3+ normal days (+10). Habit signals from the journal: bought 9:30-10:00 ET (+10), 2x+ the user's median buy (+10, needs 3 prior buys), a ticker never traded and not watchlisted (+5, needs 3 prior trades), buying back within 30 days above the sell price (+10). `score_buy` is pure (tests call it directly). Results are stored on `Trade.fomo_*` by `ensure_scored` (lazy, parallel, max 30 per call; run by `POST /trades`, `/trading-patterns`, `/fomo/summary`, the scorecard route and the inbox's newest 10 buys; `unknown` retried daily; re-run once a week has passed to fill `week_later_pct`, the patience test). `personal_record`: per-band stats, the FOMO tax (dollars vs the S&P 500 on graded chasing buys), self-tagged `fomo` buys count as chasing and are checked against the detector, and `expected_vs_market_pct` shrinks the user's average toward other real users' (`SHRINK_K` = 5; prior 0 below 10 trades). Frontend: live check in `TradeForm` (with an "add the FOMO tag" nudge), "Am I chasing this?" on `SearchPage`, `FomoCard` on the Dashboard, hints in the inbox and on review cards (`FomoCheck.jsx`). The advisor has a `check_fomo` tool and the record in its facts. Tests use the `volumes` fixture alongside `history`.
- **Trade reasons / thesis inbox** (`thesis.py`, router under `/trades`): every trade needs a *why*. `Trade.reason_tags` holds fixed categories (comma-separated slugs from `BUY_REASONS` / `SELL_REASONS`; the frontend renders chips from `GET /trades/reasons`, so add new reasons there) and `thesis_written_at` records when the reason was written. Synced trades arrive without either and are listed by `GET /trades/needs-thesis`; `PUT /trades/thesis` answers one or many trades of the same side; the inbox sends `review_months`, which sets each trade's review date to its own `trade_date` + N months (`thesis.add_months`), so old synced trades whose date has passed are auto-graded right away (an absolute `review_date` is still accepted). Answers are final (409 on re-answer) and `dont_remember` is a valid answer that needs no thesis text. `reasons_summary` (counts, outcomes per reason, don't-remember rate, hindsight rate = written >7 days after the trade) feeds both the inbox page and the advisor's system prompt (`advisor_context_section`, `describe_trade_reason` in `build_advisor_context`).
- **Holdings earnings & news** (`holdings_news.py`, `GET /holdings/news`, shown by `SidebarHoldingsNews.jsx` under the watchlist): for each held ticker, the next earnings date from `Ticker.info` (`earningsTimestampStart/End`; past dates are dropped), falling back to Yahoo's earnings calendar page (`get_earnings_dates`, needs `lxml`, always marked estimated) when info only has the last report, and up to 3 news stories from `get_news`, kept only if they name the company and ranked by keyword rules (no Claude call). In-memory cache: profiles 12h, news 30min. CDRs (`AAPL.TO`) read from the US listing (trying `X`, `X-B`, `X-A`, e.g. `BRK.TO` → `BRK-B`) only when the short name contains "CDR" and the company names match; ETFs skip both lookups. Tests use the `market_events` fixture. The frontend reloads on the `holdings-updated` window event.
- **Earnings recaps / notifications** (`earnings_recaps.py`, `GET /notifications`, `POST /notifications/read-all`, `POST /notifications/{id}/read`): when a held stock reports, Claude writes a recap (headline, what happened, what it means, sentiment) from EPS vs estimate, the price reaction (`grading.fetch_daily_closes`) and ranked headlines. Written lazily on the first `GET /notifications` after the results are out - only once Yahoo's calendar shows the *reported* EPS (so an estimated date that passes with no report never produces a recap), only for reports in the last 10 days that the user held through, max 3 new per request. `EarningsRecap` is shared per ticker + report date (the US listing for CDRs); `EarningsNotification` is per user (unique per recap, `read_at` = read). Frontend: `NotificationsBell` (sidebar brand row, polls every 30 min, fires `recaps-updated`), `NotificationsPage` (marks all read, fires `notifications-read`), and `/holdings/news` rows carry `recap` for the sidebar's "Reported" chip. Tests use the `recap_writer` fixture (fake Claude). News falls back to `yf.Search` when `Ticker.get_news` is down.
- **Accounts & email** (`accounts.py`, router under `/auth`): signup requires an 8+ character password and stores emails lower-case (lookups are case-insensitive via `find_user_by_email`); login locks an email after 10 wrong passwords in 15 min (in memory). One-time email links (`EmailToken`, only a SHA-256 hash stored, `purpose` = `verify` 48h or `reset` 30 min, max 3 per user per hour) power `POST /auth/send-verification`, `/auth/verify-email`, `/auth/forgot-password` (same answer whether or not the account exists) and `/auth/reset-password` (logs in, confirms the email, kills other reset links). Links open the frontend as `?verify=` / `?reset=`, which `App.jsx` reads once and strips from the URL. Email goes out through `emailer.send_email` (Gmail SMTP: `GMAIL_ADDRESS`, `GMAIL_APP_PASSWORD`, `APP_URL`); templates in `email_templates.py` are table-based with inline styles and always include plain text. `POST /notifications/{id}/email` ("Email me this") only sends to the user's own *confirmed* address (403 `{code: email_not_verified}` otherwise), once per 10 min per recap, 20 per day. Tests use the `outbox` fixture (fake email, configured by default).
- **Demo accounts** (`demo.py`, `POST /auth/demo`): each visitor gets a private throwaway user (`is_demo`) seeded with `DEMO_TRADES` priced at the real close on each trade's date (weekend dates move to the last session; fallback prices if history fails; the buy tagged `fomo` is moved to the hottest real day for that stock 120-200 days ago, at 9:40), some pre-graded, some due (auto-graded on first visit), three with no reason yet, plus profile and watchlist. Max 5 per IP per hour; demos older than 24h are deleted (`delete_users`) whenever a new one starts. Demo users get the smaller `demo_chat` advisor bucket, no brokerage (`is_available_for`), and no email features. The frontend shows a demo banner with "Create your free account".
- **Brokerage sync** (`snaptrade_sync.py`, routes in `brokerage.py`): `SNAPTRADE_KEY_TYPE` selects the mode. `personal`: one person's key, only the user matching `SNAPTRADE_OWNER_EMAIL` may use it (everyone else gets 403 / `available: false`). `commercial`: every user links their own brokerage; their SnapTrade user is registered on first Connect (never on page load, since SnapTrade bills per user) and stored in `snaptrade_users` with the secret encrypted by `secret_box.py` (`FIELD_ENCRYPTION_KEY`, which must never change in production). All SnapTrade calls go through `BrokerageSession`, which attaches the current user's credentials. The sync combines account *activities* (authoritative, refreshed by SnapTrade ~daily) with *recent orders* (real-time, last 24h). Each row stores `external_id` (`activity:<id>` / `order:<id>`, unique per user) so re-syncs never duplicate; an incoming record first tries to take over a matching existing row (same root symbol, ET date, action, quantity) so theses survive. Rows that can be taken over: manual/CSV rows, order rows (replaced by their activity), and rows from accounts marked `disconnected_at` (a reconnect or key switch gives accounts new ids; the new account also inherits the old one's `sync_enabled` by name). Quirks handled there: UTC timestamps → US/Eastern date/time, SnapTrade `.VN` → yfinance `.V`, sell units arrive negative, options are skipped, and US-stock prices arrive in CAD (converted with a yfinance USD/CAD rate). Only TFSA/PERSONAL accounts sync by default.

### Frontend
- **No router.** `App.jsx` switches screens with an `activeView` state string. The "Trade reasons" view (`TradeReasonsPage.jsx`) holds both halves of the journal loop as tabs: *Needs a reason* (`ThesisInbox`) and *Due for review* (`ThesisReview`, the grading scorecard), both rendered with `embedded` so the page owns the topbar; its sidebar badge counts both. The old `thesisreview` view id still opens the review tab. The gating order is: no token → `AuthScreen`; no profile (`GET /profile` fails) → `SurveyScreen`; otherwise `Layout` plus the chosen view. A 401 from `/profile` clears the token. `SurveyScreen` doubles as the profile editor through `editMode`.
- **API calls go through `apiFetch` in `src/api.js`**, which uses `VITE_API_URL` (default `http://127.0.0.1:8000`, baked in at build time) and attaches the bearer token from `localStorage`. Don't call `fetch` directly.
- `refreshKey` in `App.jsx` is bumped after a trade is logged so the dashboard reloads. `BrokerageCard` (on the Dashboard) renders nothing unless `/brokerage/status` says `available`; it syncs on mount and every 5 minutes (the backend skips syncs within 2 minutes unless `force=true`) and bumps the Dashboard's `syncKey` to reload holdings.
- `Dashboard.jsx` and `SidebarWatchlist.jsx` poll every 60s (`PRICE_POLL_INTERVAL_MS`), paired with the backend's 45s price TTL. Keep the two numbers in step.
- `src/tickers.js` is a small hard-coded ticker list used for search autocomplete.
- Theme colours are CSS variables in `src/theme.css` (e.g. `var(--color-text-secondary)`).
- **CORS** allows `localhost:5173`/`5174` plus any origins in the backend's `ALLOWED_ORIGINS` env var (comma-separated) - the deployed frontend URL must be listed there.

## Conventions
- The codebase is heavily commented in plain language, explaining *why* each piece exists, including notes marked `NEW`. Keep that style when editing.
- `Backend/requirements.txt` is plain UTF-8 with exact pins (it was UTF-16 from a Windows `pip freeze`; converted so deploy builders can read it). Keep it UTF-8.

## Deployment
- `DATABASE_URL` selects the database (`database.normalize_database_url` maps `postgres://`/`postgresql://` to the psycopg 3 driver). Only set it to the hosted Postgres in the deployed environment, never in a local `.env`.
- Apply migrations to the hosted DB from a local shell with that URL set for the one command: `DATABASE_URL=<hosted url> alembic upgrade head`.
- `scripts/copy_database.py` copies the local SQLite data into an empty target (`TARGET_DATABASE_URL`): it migrates the target, refuses to write over existing data, keeps ids and resets Postgres id sequences.
- **Live on Vercel** as two projects deployed with the CLI (the GitHub repo can't be connected because it belongs to another account): frontend `innerstock` → https://innerstock.vercel.app (root `Frontend/`), backend `innerstock-api` → https://innerstock-api.vercel.app (root `Backend/`, served through `index.py`, which re-exports `main.app`). Deploy with `npx vercel deploy --prod` from inside each folder. Env vars live in each Vercel project (`npx vercel env ls`): backend has `DATABASE_URL` (Neon **pooled** URL), `JWT_SECRET_KEY` (separate from local), `ANTHROPIC_API_KEY`, `SNAPTRADE_*`, `ALLOWED_ORIGINS`; frontend has `VITE_API_URL`.
- Hosted data is Neon Postgres. Schema changes must be applied there too: `DATABASE_URL=<neon url> alembic upgrade head` before deploying code that needs them.
- `.vercelignore` files keep `.env`, `.env.local`, local databases and `venv/` out of Vercel CLI uploads.
